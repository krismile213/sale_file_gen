# 导数自动化方案书

| | |
|---|---|
| **项目** | 日销/月销数据源自动导出（导数自动化） |
| **版本** | v1.0 |
| **日期** | 2026-10-27 |
| **范围** | 亚马逊（主账号 + interflow）、美客多、EMAG 的报告自动导出 |
| **关联系统** | `Daily_Sales_Report/pipeline/run.py`（日销表跑批）、`trunk/month_sale_file.py`（月销表 + 库龄表） |
| **状态** | 方案已定，接口层已开发，等待紫鸟权限开通后进入试点 |

---

## 一、摘要

现状每期需要从 3 个平台、13 个账号手工导出 **34 个报告文件**，加上改名、归位、核对，
单期人工投入约 40~70 分钟。本方案通过紫鸟浏览器的 WebDriver 接口 + Playwright
接管已登录的店铺窗口，实现"一键导出 → 自动命名 → 自动归位 → 自动跑批"。

**核心结论三条：**

1. **可行**。账号集中在紫鸟浏览器，登录、验证码、IP 环境由紫鸟负责，脚本不接触凭据，风险最低。
2. **必须从源头自动化**。管理库存报告本身不含站点字段（日本站除外），
   "下载后再自动归类"无法区分美国/加拿大，只能在下发下载指令时就知道站点。
3. **不影响现有流程**。自动化只负责"把文件按标准名放进快照目录"，
   `run.py` 一行不改；自动化失败时手工导出照常能跑。

## 二、背景与现状

### 2.1 现状量化（2026-10-27 快照实测）

| 类别 | 文件数 | 格式 | 来源 |
|---|---:|---|---|
| 亚马逊管理库存报告（主账号 10 站点） | 10 | csv | 卖家中心 → 报告 → 亚马逊物流 → 库存 |
| interflow 管理库存报告（5 站点） | 5 | csv | 同上（另一卖家账号） |
| 亚马逊订单报告（8 站点区域） | 8 | txt（tab 分隔） | 卖家中心 → 报告 → 亚马逊物流 → 销售 |
| interflow 订单报告（4 站点区域） | 4 | txt | 同上 |
| 美客多（Full 库存 + 订单） | 2 | xlsx | 美客多卖家后台 |
| EMAG（库存 + 订单，订单常分页成 3 份） | 4 | xlsx | Fulfilment by eMag |
| 多国库存报告 | 1 | csv | 亚马逊 |
| **日销周期合计** | **34** | | |
| 东南亚平台原始导出（备查，非每日） | 11 | xlsx | Lazada / Shopee |
| **月销周期：库龄报告** | 16 | csv/xlsx | 亚马逊物流库存 + FBE Inventory + 美客多长期仓储费 |

### 2.2 手工流程拆解

单期每个文件平均需要 5 个动作：

```
打开紫鸟 → 进入对应店铺 → 切换到对应站点 → 进报告页
  → 设置日期/筛选条件 → 点下载 → 等落盘
  → 重命名为「亚马逊<站点>管理库存报告<YYYYMMDD>.csv」
  → 移动到 trunk/data/数据归属周期/<期>/快照日期/<日期>/
```

按每文件 1~2 分钟估算，**单期 34 个文件约 40~70 分钟**；月度再加 16 份库龄报告。
人工环节的典型失败模式是**漏导**和**站点错配**（把加拿大的文件当美国放进去），
这两类错误在跑批体检时才会暴露，返工成本高。

### 2.3 痛点归纳

| 痛点 | 影响 |
|---|---|
| 重复点击量大 | 单期 200+ 次点击，占用大量工作时间 |
| 文件命名靠手工 | 错一个字符跑批就报缺文件 |
| 站点与文件易错配 | 数据串站，跑批结果错但不报错（最危险） |
| EMAG 订单会分页 | 月底需要人工判断合并，已有脚本但需手动触发 |
| 依赖个人记忆 | 换人接手困难 |

## 三、目标

| 编号 | 目标 | 衡量标准 |
|---|---|---|
| G1 | 单期导数从 40~70 分钟降到 5 分钟以内（含人工确认） | 实测计时 |
| G2 | 文件名与站点零错配 | 跑批体检连续 10 期零"缺报告/导错账号"红灯 |
| G3 | 失败可回退 | 自动化失败时，手工导出放进去仍能正常跑批 |
| G4 | 不引入新的账号安全风险 | 脚本不接触卖家账号密码，全程在紫鸟环境内操作 |

**非目标**：不做数据加工逻辑的改动，不改染色规则、不改跑批口径。

## 四、技术约束（本方案的关键前提）

### 4.1 管理库存报告不含站点字段

实测 26 列全部是商品维度字段（`sku` / `asin` / `afn-*` 等），**没有 marketplace 列**。
只有日本站因为导出的是日文表头，可以靠编码识别。

**推论**：任何"下载完成后按内容自动改名"的方案，对 15 份管理库存报告都不可靠
——美国站和加拿大站的文件内容结构完全一致。

### 4.2 因此只有两条路

- **路一**：在下发下载指令时就知道站点（浏览器自动化 / 官方 API）
- **路二**：人工标注站点（等于没省时间）

本方案走路一。

### 4.3 其他约束

| 约束 | 说明 |
|---|---|
| 订单报告按"最后更新日期"导出 | 会混入上月尾巴，属设计内，跑批已按列头月份隔离 |
| EMAG 订单报告可能分页 | 已有 `merge_emag_orders.py` 自动合并，无需改 |
| 部分库存报告 GBK 编码 | 澳/日/interflow澳 三份，跑批已有兜底 |
| 跑批依赖固定文件名 | 自动化必须产出与 `config.py` 声明完全一致的文件名 |

## 五、方案选型

### 5.1 候选方案

| | 方案 | 做法 |
|---|---|---|
| **A** | 紫鸟 WebDriver + Playwright | 紫鸟客户端开 web_driver 模式，`startBrowser` 返回 CDP 调试端口，Playwright 接管已登录窗口，操作页面点下载 |
| **B** | 亚马逊 SP-API 等官方接口 | 注册开发者，用 Reports API 拉报告；美客多/EMAG 各有 API |
| **C** | 仅做下载后归位 | 监视下载目录，识别类型、改名、移动 |

### 5.2 对比

| 维度 | A 紫鸟 + Playwright | B 官方 API | C 仅归位 |
|---|---|---|---|
| 能否解决站点识别 | ✅ 下载时站点已知 | ✅ 请求自带 marketplaceId | ❌ 无法区分站点 |
| 账号凭据暴露 | 无（紫鸟内部完成登录） | 需存 LWA 密钥 | 无 |
| 风控风险 | 低（真实环境、真人节奏） | 无 | 无 |
| 上线周期 | 1~2 周 | 3~6 周（开发者审核 + 多账号授权） | 2~3 天 |
| 页面改版影响 | 有，需维护 | 无 | 无 |
| 覆盖范围 | 三平台全支持 | 亚马逊最完整，EMAG 需申请权限 | 仅限内容可识别的报告 |

### 5.3 选型结论

**采用方案 A 作为主线，方案 B 作为中期演进方向。**

理由：

1. 方案 C 因 4.1 的约束，对 15 份核心库存报告无效，不能作为主方案。
2. 方案 B 最稳，但需要注册开发者账号、逐账号授权，周期长；且 EMAG 的 API 权限不确定。
3. 方案 A 的登录环节由紫鸟承担——用户实际使用紫鸟的"自动识别验证码"能力，
   脚本完全不接触卖家账号密码，安全边界清晰。
4. A 与 B 不冲突：A 跑通后即可产出数据，B 审批下来可平滑替换下载层，
   接口层（`ziniao_api.py`）与任务层分离，替换成本低。

## 六、总体架构

```
┌─────────────────────────────────────────────────────────┐
│  调度层  run_download.py                                 │
│  按「平台 → 店铺 → 站点 → 报告」遍历任务                  │
└───────────────┬─────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────┐
│  浏览器层  ziniao_api.py（已完成）                        │
│  start_client → getBrowserList → startBrowser            │
│  → debuggingPort → Playwright connect_over_cdp           │
└───────────────┬─────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────┐
│  任务层  amazon_inventory.py / amazon_orders.py / ...    │
│  进报告页 → 设条件 → 点下载 → 等落盘                      │
└───────────────┬─────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────┐
│  归位层  按站点重命名 → 移到 快照日期/<YYYYMMDD>/         │
└───────────────┬─────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────┐
│  现有流程  pipeline/run.py（不改）                        │
│  体检 → 跑批 → 缺货表 → 归档                              │
└─────────────────────────────────────────────────────────┘
```

**分层原则**：浏览器层只负责"把窗口交出来"，任务层只负责"在窗口里点东西"，
归位层只负责"把文件放对地方"。任何一层出问题，其余两层不受影响。

## 七、技术实现要点

### 7.1 紫鸟本地接口

| 项 | 值 |
|---|---|
| 通信地址 | `http://127.0.0.1:{port}`，默认 **16851** |
| 协议 | HTTP POST，JSON body，用 `action` 字段区分命令 |
| 公共字段 | `requestId`（uuid）+ `company` / `username` / `password` |
| 启动参数 | `--run_type=web_driver --ipc_type=http --port=16851` |
| 返回码 | `statusCode`：`0` 成功，`-10003` 登录失败 |

命令清单：

| action | 作用 | 关键返回 |
|---|---|---|
| `updateCore` | 更新内核到 webdriver 所需版本 | — |
| `getBrowserList` | 获取店铺列表 | `browserList[]`（含 `browserName` / `siteId` / `browserOauth`） |
| `startBrowser` | 启动店铺环境 | `debuggingPort` / `downloadPath` / `launcherPage` / `ipDetectionPage` |
| `stopBrowser` | 关闭店铺 | — |
| `exit` | 退出客户端 | — |

**两个关键参数：**

- `notPromptForDownload = 1` —— 下载不弹保存对话框，文件直接落到 `downloadPath`，
  脚本可以盯目录等文件出现。
- `debuggingPort` —— 店铺窗口的 CDP 端口，Playwright 用
  `chromium.connect_over_cdp("http://127.0.0.1:<port>")` 接管，**不需要 chromedriver**。

> ⚠️ 普通模式的紫鸟客户端不响应接口调用，必须以 web_driver 模式重启。
> 脚本用 `--kill` 参数控制是否强制重启，避免打断用户正在进行的操作。

### 7.2 下载落盘与命名

```
紫鸟 downloadPath（由紫鸟管理）
   ↓ 文件出现后 2 秒内检测到
重命名为  <账号前缀><站点><报告类型><YYYYMMDD>.<ext>
   ↓
移动到  trunk/data/数据归属周期/<YYYYMM>/快照日期/<YYYYMMDD>/
```

命名规则严格对齐 `pipeline/core/config.py` 里声明的文件名模板，
保证 `run.py` 的体检逻辑无需任何改动。

### 7.3 站点识别策略

不依赖文件内容，而依赖**任务上下文**：

```
店铺 A（主账号）
  ├─ 站点 US  → 下载 → 命名「亚马逊美国管理库存报告20261027.csv」
  ├─ 站点 CA  → 下载 → 命名「亚马逊加拿大管理库存报告20261027.csv」
  └─ ...
```

站点与文件名的映射表写在任务配置里，与 `config.py` 的 `REPORT` 声明同源，
避免两处维护。

## 九、风险与应对

| 风险 | 等级 | 影响 | 应对 |
|---|---|---|---|
| 紫鸟接口或页面改版 | 中 | 脚本失效，导数中断 | 分层设计，只改任务层；保留手工导出流程作为永久兜底 |
| 下载超时/文件未落盘 | 中 | 缺文件 | 每个任务带超时 + 重试；失败清单汇总，人工补导 |
| 站点错配 | 高 | 数据串站，且跑批不报错 | 站点由任务上下文决定，不靠内容识别；跑批体检的 SKU 匹配率闸可二次发现 |
| 紫鸟权限被收回 | 低 | 自动化停摆 | 专用账号权限独立管理；文档记录开通步骤便于恢复 |
| 并发打开过多店铺 | 中 | 本机资源不足/被限流 | 默认串行，可配置并发数上限（建议 ≤3） |
| 密码明文存储 | 中 | 凭据泄露 | `config.json` 不入版本库；使用专用自动化账号，权限最小化 |

## 十、与现有流程的关系

**本方案对现有系统零侵入：**

| 现有组件 | 是否改动 | 说明 |
|---|---|---|
| `pipeline/run.py` | 否 | 只认快照目录里的标准文件名 |
| `pipeline/core/config.py` | 否 | 文件名模板是自动化的命名依据，不反向修改 |
| 染色规则 / 条件格式 | 否 | 完全不涉及 |
| 缺货表 `shortage_report.py` | 否 | 随跑批自动出 |
| 库龄表 `age_report.py` | 否 | 随月销表自动出 |
| 归档逻辑 | 否 | 跑批后照常归档 |

**回退路径**：自动化任何环节失败，均可退回手工导出 + 手工放入快照目录，
`run.py` 的行为完全一致。这满足"做重大变更时优先保证旧功能完善"的要求。
