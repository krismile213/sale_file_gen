## 二、口径链路（先把「沙特」和「欧洲」是怎么分出来的讲清楚）

主脚本 `get_belonging_amazon_order_df()`（L178~231）**不是按报告内容筛国家，而是按文件名取报告**，国家是**报告内字段映射**出来的：

```
报告文件（按文件名取）
   ↓  sales-channel 字段
channel_country_map        # L49~69   Amazon.sa→沙特阿拉伯 / Amazon.de→德国 / Amazon.co.uk→英国 …
   ↓  得「站点」
amazon_country_inv_map     # L28~48   德国/法国/意/西/荷/波/瑞/爱/比/土→「欧洲」；英→「英国」；沙特→「沙特阿拉伯」
   ↓  得「仓库」
月销总表列（L1648~1649）
   仓库 == "沙特阿拉伯"  →  月销总表「沙特」列
   仓库 == "欧洲"        →  月销总表「欧洲」列
   仓库 == "英国"        →  月销总表「英国」列（英国**不并入**欧洲，是既定口径）
```

关键点：**每一份报告、每一个 `sales-channel` 只映射到唯一一个「仓库」**，而月销总表是按「仓库」等值切分的 → **结构上不可能把同一行算进两列**。

> 左右两套映射都是**多对一**、且值域**互斥**：`Amazon.sa` 只去沙特，`Amazon.de/fr/it/es/…` 只去欧洲。没有一条 channel 同时指向两者。

### 证据 2 — 跨报告 `(订单号, SKU)` 重叠 = 0

把 **巨川 7 份 + interflow 3 份**共 10 份报告两两做交集（先剔除 `order-status=Cancelled`、`Amazon.Found.`、`amzn.gr.`）：

```
>>> 跨报告 (amazon-order-id + sku) 重叠总数 = 0
```

### 证据 3 — 报告内「同 (订单号,SKU) 多行」不是重复

| 报告 | 同 (订单号,SKU) 多行组数 | 性质 |
|---|---:|---|
| 亚马逊欧洲 | 10 | 见下，全部无害或应相加 |
| 亚马逊北美 | 8 | 同上 |
| 亚马逊日本 | 1 | 同上 |
| 其余 7 份 | 0 | — |

两类，都不是重复：

- **① `item-status = Cancelled` 且 `quantity = 0`** —— 取消附属行（Amazon 保留原行 + 取消行）。加 **0**，不改销量。欧洲 4 组、北美 4 组、日本 1 组。
- **② 两行都 Shipped，但 `order-item-id` 不同** —— 同一订单里该 SKU 的**多笔购买**，**应当相加**。实例：

  | 订单号 | order-item-id | quantity | item-price |
  |---|---|---:|---:|
  | 028-4740591-1142765 | 67508327872282 | 4 | 47.96 |
  | 028-4740591-1142765 | 67312378286842 | 1 | 11.99 |
  | | | **合计 5** | 59.95 |

  其余同理：`304-9439105-5776311` 1+3=4、`406-1008720-7245955` 4+6=10、`408-6761219-0998746` 1+2=3。
  单价 × 数量自洽 → 是真实的多件购买，**脚本按 SKU 求和是对的**。

## 五、顺带查出的隐患与附加对比（**都不影响当前出数**，但你要知道）

### A. 跨「实体」有 16 个订单号重复 —— 唯一"未来可能真的重复"的点

| 组合 | 共同订单号数 |
|---|---:|
| 亚马逊\|北美 ∩ interflow\|北美 | 14 |
| 亚马逊\|澳大利亚 ∩ interflow\|澳大利亚 | 2 |

**但每条的两个 SKU 都完全不同**，例如：

| 订单号 | 巨川侧 | interflow 侧 | 渠道 |
|---|---|---|---|
| 111-2357268-5709867 | G517 ×1 | G555 ×1 | Amazon.com |
| 111-5845831-1788229 | G520 ×4 | G544 ×1 | Amazon.com |
| 112-5941880-1511469 | G278 ×1 + G325 ×1 | G551 ×2 | Amazon.com |
| 701-9841266-9518649 | G458 ×1 | G542 ×1 | Amazon.ca |

→ **`(订单号, SKU)` 不重叠 ⇒ 当前不是重复计数**（证据 2 已证全表为 0）。
→ 但 Amazon 订单号理论上全局唯一，同一单号出现在两个主体、装的还是不同 SKU，**建议向数据部确认**这两个主体是不是共用一套订单中心 / 代运营关系。
→ ⚠️ **真正的风险**：月销总表「美国」列 = `仓库=="美国"`，**不分实体**（实体不是月销表的切分维度）。一旦哪天两边出现**相同 `(订单号, SKU)`**，两行都会落进「美国」列 → **直接双计**。

### B. `Non-Amazon*` 渠道被整体丢弃（合计 75 件）

10 份报告里 `sales-channel` 为 `Non-Amazon` / `Non-Amazon DE` / `Non-Amazon IT` / `Non-Amazon ES` / `Non-Amazon US` / `Non-Amazon CA` 的行，因 `channel_country_map` 无映射 → `站点` 为 NaN → L196 被 `notna()` 过滤掉。

| 报告 | 丢弃件数 |
|---|---:|
| 欧洲 | 42 |
| 北美 | 10 |
| 日本 | 7 |
| 澳大利亚 | 5 |
| 沙特 | 4 |
| 阿联酋 | 4 |
| 印度 | 3 |
| **合计** | **75** |

这是**有意义的口径**还是**无意漏算**，需要业务确认。**本身不是重复问题**，但既然在对账时露头了，一并记下。

#### B-1. 定性：这就是 **MCF（多渠道配送）**，不是普通亚马逊单（2026-10-12 补充）

把 72 行有效 `Non-Amazon` 的原始字段全量拉出来，四条特征同时成立：

| 字段 | 取值 | 含义 |
|---|---|---|
| `fulfillment-channel` | **全部 = `Amazon`**（不是 `Merchant`） | 由**亚马逊物流/FBA 库存**发货 |
| `sales-channel` | `Non-Amazon` / `Non-Amazon DE/IT/ES/US/CA` | 成交渠道**不是**亚马逊站点 |
| `amazon-order-id` | **`S01-`(北美) / `S02-`(欧洲) / `S03-`(日本) 专用号段** | 亚马逊给非亚马逊渠道单的独立号段 |
| `merchant-order-id` | `gift-000001`、`U6P2gNiv0U`、`302-…-WS` | **卖家自建渠道单号**（独立站/礼品单/其他平台） |

⇒ 业务实质：**卖家在亚马逊之外的渠道卖出，但用亚马逊 FBA 库存发货**。对亚马逊而言"非亚马逊销售渠道"。

#### B-2. 三个事实（2026-10-12 实测）

1. **不会重复**：`S01/S02/S03` 号段共 71 个单号，与**正常已计单号交集 = 0**（独立号段）。丢弃它们既不重复、也不回填。
2. **83% 无法归属国家**：72 行里仅 12 行有 `ship-country`（CA 1 / US 2 / IN 2 / JP 2 / DE 1 / IT 2 / ES 2），**60 行（83%）该字段为空** → 无收货地可依。
3. **同款商品另有亚马逊渠道在卖**：58 个 `Non-Amazon` SKU 中 **38 个**同时出现在正常已计行 → 是"同款走不同渠道"，不是独有商品。
4. 另：欧洲报告里 **22 行 `amzn.gr.*`** 也属此类（同 `S02-` 号段），主脚本 L198 本来就有专门过滤 —— 结论同上。

#### B-3. 建议：**维持不计入**，但必须留痕 + 监控（2026-10-12）

**倾向不计入**，三条理由：

- **口径不同**：月销总表统计的是"通过 Amazon 站点成交"的量；MCF 是"非亚马逊渠道成交"。混进去会污染「亚马逊各国销量」的定义，下游采购会把它当成亚马逊站点需求来备货。
- **归属不可复现**：83% 无 `ship-country`，要落列只能按"报告归属"人为指定（出现在欧洲报告就算欧洲仓）—— 且**当前架构下即使放开 L196 过滤也落不进任何列**（月销表按 `仓库` **等值**切分，`NaN` 不等于任何值）。
- **量级微小**：75 件 / 62,837 = **0.12%**，对采购决策无实质影响；而误计入带来的口径混乱成本 > 收益。

**但要避免"静默丢弃"**（本项目最大雷区）：

- 本文已把口径与原因写明（此处）；
- 建议在只读体检工具里加一条统计：**每月打印 MCF 件数与占比**，超过阈值（如 ≥1% 或 ≥500 件）即提示复核。

**若业务确实要"总出货量口径"（含 MCF）**：不要直接放开 `站点.notna()`（会留 `仓库=NaN` 脏行且仍落不进列），而应 ①**按报告归属（`订单组`）映射到仓库**；②在月销表**单列**一列「MCF/非亚马逊渠道」，两个口径并存。

### C. 沙特的库存报告从未被读取（库存根本不进月销总表）

- 主脚本全文 **只调用一次** `get_manage_inv_df("欧洲", …)`（L1432），且结果只用于生成备货计划的 SKU 清单 `current_sale_df`。
- 全文 `库存` 仅 3 处命中，**没有任何一处把库存数值写进月销总表**。
- `亚马逊沙特阿拉伯管理库存报告20261006.csv`（120KB）**在管线里从未被打开**。

→ 所以「库存重复」这件事**根本不存在**（脚本不产生月销表的库存列）；
→ 但如果业务需要沙特的**在库/在途**，目前**完全没有进管线** —— 这属"**缺失**"，与重复是两回事，要不要补由你定。

### D. 沙特 vs 阿联酋：报告"长得一模一样"，但"内容各是各的"（2026-10-12 补充）

快照目录里与这两个国家相关的共 **6 份文件**（巨川两国 × 订单/库存 = 4 份，interflow 阿联酋 2 份）：

| 类别 | 文件 | 行数 | 列数 | MD5 是否相同 |
|---|---|---:|---:|---|
| 订单 | `亚马逊沙特阿拉伯站点202609订单报告.txt` | 1,679 | 30 | 否 |
| 订单 | `亚马逊阿拉伯联合酋长国站点202609订单报告.txt` | 1,057 | 30 | 否 |
| 订单 | `interflow阿拉伯联合酋长国站点202609订单报告.txt` | 32 | 34 | 否 |
| 库存 | `亚马逊沙特阿拉伯管理库存报告20261006.csv` | 411 | 24 | 否 |
| 库存 | `亚马逊阿拉伯联合酋长国管理库存报告20261006.csv` | 392 | 24 | 否 |
| 库存 | `interflow阿拉伯联合酋长国管理库存报告20261006.csv` | 48 | 24 | 否 |

**结论：结构完全一样，内容完全不一样。**（6 份 MD5 全不同 ⇒ 不是同一份被复制两次）

- **结构**：沙特与阿联酋的**订单报告列名逐一相同**（同 30 列、同顺序、同 `utf-8`）；**库存报告同样同 24 列**。因为都出自同一套亚马逊导出模板，**除文件名外没有格式差别**，读表代码可共用。
- **内容**：站点不同 —— 沙特报告 `sales-channel` = **`Amazon.sa` 1,675** + Non-Amazon 4；阿联酋 = **`Amazon.ae` 1,053** + Non-Amazon 4。**订单号交集 = 0**（1,641 单 vs 1,042 单）。
- **但商品高度重叠**：订单 SKU 沙特 267 个 / 阿联酋 233 个，**交集 191**；库存 SKU 沙特 411 / 阿联酋 392，**交集 387**。
  ⇒ 同一批货在两个中东站点**并行铺货**，销量与库存**各自独立记录**（不是同一批数据换个国家名）。

**两个要留意的点（2026-10-12）**：

1. **阿联酋是"两实体合流"**：主脚本 `juchuan_sale_groups`（L1440）含 `阿拉伯联合酋长国`，`interflow_sale_groups`（L1441）**也含**它
   → 巨川与 interflow 的阿联酋订单**都会落进月销表「阿联酋」列**（L1590；月销表按 `仓库` 切分、**不分实体**）。
   这正是 §五-A「跨实体 16 个订单号」里的阿联酋那 2 个。当前 SKU 不同 ⇒ **不重复**；仍是潜在双计点。
2. **3 份库存报告全部没进管线**：主脚本只读 `亚马逊欧洲管理库存报告…csv`（而该文件本期仅 **534 B**，是空表）；
   沙特、阿联酋（含 interflow）的库存报告**从未被打开** —— 与 §五-C 同因。

## 六、附带记录：一个会静默失效的列名坑

亚马逊订单报告（以**欧洲**报告为例）共 41 列，**最后一列名为 `order-item-id ` —— 尾部带一个空格**。

> ⚠️ 另注意：**各站点导出的列数并不一致** —— 欧洲 **41 列**，沙特 / 阿联酋只有 **30 列**（见 §五-D）。
> 所以别把某一国的列数当成通用假设来写死代码。

- 将来若有人想按 `order-item-id` 去重/对账，写成 `df["order-item-id"]` 会 **KeyError 或静默取不到**；
- 且该列**不在**主脚本现有的任何 SKU 过滤/聚合逻辑里，所以现在无影响，只是埋了个雷。
