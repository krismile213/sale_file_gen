## 五、★ 本期（2026-10-07）新发现并修复的四个数据问题

### 5.1 eMAG 9 月销量显示为空（实际有销量）

**现象**：`EMAG全站点202609订单报告.xlsx` 有 149 行订单，但月销总表 `eMAG` 列 9 月 = **0**。

**根因**：该报告**列名是中文**（`订单编号/订单日期/产品代码/数量/订单状态`），而脚本按**英文列名**取值。
中文表里没有 `sku` 列 → 汇总后 SKU 为空 → 被第 1439 行"丢弃空白 SKU"清洗**整批丢掉** —— 因此**既不报错也不计销量**（静默丢单，最危险的一类）。

**证据**：

| 期 | 报告列名（前 8 列） |
|---|---|
| 202608 | `Order number / Order date / AWB number / Product name / Product code / …`（英文） |
| 202609 | `订单编号 / 订单日期 / 空运提单号码 / 产品名称 / 产品代码 / …`（中文） |

**修复**：`get_belonging_emag_order_df` 加中文→英文别名映射（L733~740）。

**修复后**：eMAG 9 月 = **135**（= 149 行 − 8 笔 `Canceled by customer` − 6 笔 `Storno`），8 月为 92。

### 5.2 得分列（`【2026年】KH` 与 `【欧洲各国】EP`）还是 7 月得分

**现象**：`2026年-欧洲各国每月销售情况` 的 `EP(146)` 列表头仍是 **`7月销量得分`**，值也是 7 月的。

**根因**：得分列在模板里是**静态值**（无公式），脚本原本**只在补新 SKU 时才写**。
本期的 `月销售总表.xlsx` 模板是**沿用 202608 成品**（`KH` 表头被改成 `8月销量得分`，**值没换**）——
实测 `202609 模板 KH 与 202608 成品 KH 逐行完全相同（545/545）`，即整列都是 7 月值。

**口径确认**（用数据部 202608 原始模板反查）：

| 模板 | `【2026年】KH` 表头 | `【欧洲各国】EP` 表头 | KH 与 EP 逐 SKU 对比 |
|---|---|---|---|
| 数据部 202608 原件 | `7月销量得分` | `7月销量得分` | **497 个同名 SKU 值完全相同（0 不同）** |

⇒ **EP 就是 KH 的同源镜像列**，两者都必须等于**当月得分**（`商品资料[score_col_name]`）。

**修复**：新增两处自愈写入（L1499~1509 刷 KH、L1703~1729 刷 EP），以 `商品资料.xlsx` 为权威。

**修复后核对**：

| 核对项 | 结果 |
|---|---|
| `【2026年】KH` 表头 | `8月销量得分` ✅ |
| `【欧洲各国】EP` 表头 | `8月销量得分` ✅ |
| KH vs EP（497 个同名 SKU） | **不一致 0 行** ✅ |
| KH vs `商品资料.8月销量得分` | 可比 422 行，**不一致 0 行** ✅ |
| 变更量 | KH 命中 403 行、**变更 43 行**；EP 回填 389 行 |

> ⚠️ **根因不在代码，在模板**：正确做法是让 数据部 提供**本期新版的 `月销售总表.xlsx`**（得分列每个月由他们刷新）。

### 5.3 【2026年】KJ 列（当年总销量）停在 8 月 —— 写表列位错一位

**现象**：月销总表 `【2026年】` 的 `KJ(296)` 列（表头 = `=$B$1&"总销量"`）数据行合计 = **532,372**（只到 8 月），
而 9 月已出、应当 = **595,009**（用户报"总表销量还是 53w"）。

**定位过程**：

| 步骤 | 发现 |
|---|---|
| 1 | 全表扫 50~56 万 → 在 202609 成品里**只在 KJ 列命中**；`【2021-2026年销量情况】G14` 已是 595,009（对的） |
| 2 | 读 KJ 单元格：是**静态值**（3590…），不是公式；行4 的 KJ=3590 恰等于该行 1~8 月之和 |
| 3 | 读脚本 L1588~1597：`processed_month_sale_df[f"{year}年总销量"] = 总计块月列之和` |

## 2026-11-02 · `trunk/age_report.py`：「取数清单」改成只列**真正入表**的文件

### 症状（跑 202610 库龄时发现）

一张「取数清单」写着 **50 个文件 / 9,975 行**，而「本期明细」只有 **4,661 SKU**。
差额不是丢数据，而是**清单在撒谎**：`sources` 在解析循环里就把每个文件登记进去，

`sources` 没跟着过滤 → 旧快照（20261023 那一批 16 个文件）**一件没进表，却全列在清单上**。

为什么危险：这张表的定位是"这一期到底吃了哪些文件"，审计口径全靠它。
清单多列 33 个文件，等于让人无法判断某个站点到底用的是哪一天的库存。

### 改法

解析循环里改成先攒 `file_items = [(文件名, 格式, 解析结果)]`；
`latest_snapshot_only()` 之后，用保留下来的 item 对象 id 反查每个文件**实际入表几行**：

- 入表 0 行 → 打印 `[忽略] xxx.csv —— 同站点存在更新的快照，本文件未入表`，不写进清单；
- 入表 N 行 → 清单记 N（原来记的是"解析了多少行"，两者混放会让人以为是求和）。

### 验证（202610 实测）

|---|---|---|

| 5 | 历史汇总 | 仍为 202610 单期 17 行（同期覆盖，幂等） ✅ |

| `北美/2026年北美销量表North America Sales table.xlsx` | `result/北美销量表/<上期>/` |
