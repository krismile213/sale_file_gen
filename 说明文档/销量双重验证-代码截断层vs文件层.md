## 1. 为什么要"双重"，单看一边会怎样

两条链各自的失效模式是**互补**的，所以必须两边都读：

| 只看文件会踩的坑 | 只看代码会踩的坑 |
|---|---|
| **模板 ≠ 结果**：`data/.../月销售总表.xlsx` 是读取源，看错文件会把"没有值"当成"算错了" | **裸表达式**：`order_df[(...)]` 不赋值 = 白算，且不报错（任务⑧ 前就是这样） |
| **公式无缓存值**：openpyxl 写的公式 `<f>SUM()</f><v />`，程序读是 `None`（但 Excel 打开会自动重算） | **rename 静默跳过**：键不存在时不报错 → 列名没改 → 整块归零（任务⑨ 前东南亚清零过） |
| **"谁打开过"会改变文件**：被 Excel/WPS 保存过之后，公式变带缓存值，读取结果前后不同 | **列名随 pandas 版本变**：`数量` / `数量dropna`，旧写法直接静默失配 |

**所以判据不能是"某个数看起来对"，而必须是"两条独立路径算出同一个数"。**

## 2. 第一重：代码 / 截断层

### 2.1 数据流与 4 个截断点

```
源报告(data/数据归属周期/202608/快照日期/20260907/)
      │  T1 归属周期截断 · T2 快照截断 · T3 状态截断
      ▼
各平台订单表 → 按 SKU 聚合
      │  T4 SKU/ASIN 规范化
      ▼
total_sku_sale_df.csv（7287 行，全渠道长表）  ← ③ 口径复算的输入
      ▼
processed_month_sale_df.csv（545 行 × 298 列）  ← ④ 中间产物的输入
      ▼
result/.../月销售总表.xlsx                    ← ① ② 文件层的输入
```

| 截断点 | 代码位置 | 实际做了什么 | 可验证量 |
|---|---|---|---|
| **T1 归属周期** | 源报告文件名 / 报告自身范围 | ⚠️ **代码不做日期过滤**——第 198 行按日期过滤是**注释状态**；归属月完全由"源报告本身的范围"决定 | 原始报告日期 min/max |
| **T2 快照** | 第 198 / 520 行 | ⚠️ 同样**注释状态**（"去除快照日期当天订单"并未执行） | 原始报告日期 max |
| **T3 订单状态** | 亚马逊 193 行；Shopee 354-366；Lazada / Tiktok 各自 `status_map` | 亚马逊剔除 `Cancelled`；东南亚三平台走 `status_map` + **退货窗口前缀归一化**（原文带 `until <日期>` 后缀，只能 `startswith`）；过滤后 `assert` 非空 | `order-status` 取值集合 |
| **T4 SKU / ASIN** | 1104-1105（空 SKU 丢弃）；ASIN 反查 + 剥尾部字母兜底 | 空 SKU / 纯空格丢弃；亚马逊订单按 ASIN 反查主 SKU，未命中时剥尾部 1~3 位字母兜底 | 未命中 ASIN 清单 |

> **要点**：T1/T2 不是"代码截断"，而是"源报告已经截好了，代码原样接收"。所以验证时**不能**用代码去复算日期区间，
> 只能核对源报告的日期范围是否符合预期。这是一个容易误判的地方。

### 3.2 读取陷阱（不踩这三个，验证结论一定错）

1. **`data_only=True` 只能读到"缓存值"**
   脚本原始产物的公式格是 `<f>SUM(...)</f><v />`，**没有缓存值** → 读出来是 `None`。
   （但 workbook.xml 带 `fullCalcOnLoad="1"`，Excel/WPS 打开会自动重算，所以人眼看不到空。）
2. **"有没有人打开过"会改变文件**
   当前这份成品（9.14 14:41）**被 Excel/WPS 打开并保存过** → `fullCalcOnLoad` 消失、公式变成带缓存值的共享公式，
   `data_only=True` 现在**能**直接读到值。→ **同一个脚本产物，读取结果取决于之后有没有人保存过它。**
   → 所以本次验证用了 ①② 两路：① 读缓存值，② **独立逐格求和**（不依赖缓存、不依赖公式）。
3. **停售 + 当月为 0 的行，月列写的是文本 `"00"`**
   求和前必须 `to_numeric`，否则 `sum()` 会当成字符串拼接或抛错。本次验证脚本已统一处理。
