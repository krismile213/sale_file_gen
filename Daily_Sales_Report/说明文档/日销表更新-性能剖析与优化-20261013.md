# 日销表每日更新 · 性能剖析与优化（2026-10-13）

> **结果先说：整轮跑批 218 秒 → 31.5 秒（6.9 倍），已通过逐部件核验。**
> 瓶颈不是业务逻辑，是 openpyxl 把 **11MB 的透视缓存记录**整个建模再回写，
> 而它本来就要被原样写回文件里。改成"加载前换空壳 + 保存后按原字节回填"即可。

## 二、真正的瓶颈：pivotCacheRecords

openpyxl 的 `WorkbookParser.pivot_caches` 会把透视缓存记录**整个建模成 Python 对象**，
保存时再**原样序列化回去**：

```
RecordList.from_tree 建模 4.68s + to_tree 回写 5.06s + XML 解析 0.43s ≈ 10.2s（孤立测量）
```

孤立测量只值 10 秒，但**放进真实 load/save 流程后实测省 190 秒**——
说明 openpyxl 在完整流程里对透视缓存的处理远比孤立调用昂贵
（缓存字段与记录的交叉引用、写盘路径上都踩到了）。

**关键点：这部分数据最后本来就要按原样写回文件**（`restore_parts()` 每次都会重写整个 zip，
且 `refreshOnLoad` 已经靠它打上）。所以让 openpyxl 解析它一遍是**纯粹的浪费**。

## 三、已落地的改动（`daily_update/runner.py`）

### 1. pivotCacheRecords 空壳加载 + 原字节回填 ⭐ 主要收益

- `strip_pivot_records()`：把 `pivotCacheRecords*.xml` 换成
  `<pivotCacheRecords count="0"/>` 空壳再交给 openpyxl 加载。
  **部件名 / rels / `[Content_Types]` 一律不动**，所以 openpyxl 仍会写出同名部件。
- `restore_parts()`：把 `xl/pivotCache/` + `xl/pivotTables/` **按原字节覆盖**回去，
  比 openpyxl 重新序列化更保真；`refreshOnLoad="1"` 仍旧打上；
  若 openpyxl 整个丢了某个 pivot 部件，补回时同步补 `[Content_Types]` 的 Override。
- 无透视件的簿 `nstripped=0`，直接用原文件，**零影响**。
- 逃生开关：`DSR_NO_PIVOT_STRIP=1` 可退回老路（本次 A/B 对照就是用它对跑的）。

### 2. `os.replace` 兜底

本机 `os.replace` 偶发 `PermissionError [WinError 5]`（WPS/资源管理器占着文件）。
改为失败时 `shutil.copyfile` + `os.remove` 兜底，不再让整本簿更新失败。

### 3. `--jobs N` 并行调度

多进程跑多本簿；子进程 stdout 原样带回按顺序打印，单本失败不影响整批（容错与原来一致）。
> 注：当前快照下只有一本在干活，此项暂无收益；月底多站报告齐了才划算（约 1.3 倍）。

## 五、还发现的三个数据卫生问题（与性能无关，建议排掉）

1. **两个库存 sheet 各拖 2 万行垃圾行**：`英国可售+在途库存` dimension 到 `AD20750`、
   `欧洲可售+在途库存` 到 `AD21561`，真实数据只到 r701/r460。
   r702 之后每行只剩一个 `<c r="AD800" s="10"><f t="shared" si="23"/><v>0</v></c>`——
   AD 列残留 shared formula。正是代码注释里警告的"dimension 虚胖"，
   且 `_last_data_row` 每次都会把这 2 万行扫一遍并实例化空格。
2. **openpyxl 把共享字符串改成 inlineStr**：`每日销售数据` XML 18.84 MB → 33.73 MB（+79%）。
   墙钟没变慢（瓶颈是建对象不是解 XML），但文件变大、WPS 打开变慢。
3. **`restore_parts` 在没有东西可回填时也会整包重压一遍**（欧盟簿约 0.84 s），
   `回填0部件 pivot刷新0处` 时其实可以原样不动。
