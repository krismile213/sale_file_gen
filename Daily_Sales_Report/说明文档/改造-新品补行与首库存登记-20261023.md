## 一、三条拍板

| # | 决策 | 落地方式 |
|---|---|---|
| 1 | 补行范围 | **只补「本月新出现」的**（首现日期 ≥ 当月 1 号），9 月及以前的老 SKU 不追溯 |
| 2 | D 列状态 | 按库存报告 `afn-listing-exists` 自动：Yes→「在售」，No→「未上架」 |
| 3 | 粉色断货标记 | 加 `$D{行}<>"未上架"` 排除，没上架的不算断货、不标玫红 |

北美那 153 个老漏项（9/7 就首现的 62/65 个）**没有补** —— 一次灌 150+ 行没意义，还会把断货标记铺满。

## 二、改了什么

### 1. `core/analysis.py`

| 新增/改动 | 作用 |
|---|---|
| `source_sheets_of(ws, wb)` | 按命名规律找分析表的库存源 sheet，**返回列表**（Interflowd澳 = 可售库存 + 在途库存 要合并） |
| `listing_skus(ws)` | 从库存源取 `[(sku, 品名, listing是否活着)]`；标准报告读 `afn-listing-exists`，自建「可售库存」无此列则**出现即视为在售** |
| `listing_skus_merged(wb, sheets)` | 多源合并去重 |
| `append_sku_rows_auto(..., state_map=)` | 新增 `state_map` 参数，补行后显式覆盖 D 列（`clone_row` 会照抄末行的「在售」，必须改） |

> 为什么不用公式解析源 sheet：公式有 `'xx'!` 带引号和不带引号两种写法
> （欧盟是 `SUMIF('欧洲可售+在途库存'!A:A,...)`，印度是 `SUMIF(在途库存!A:A,...)`），
> 且 `data_only=True` 加载时根本读不到公式。命名规律更稳。

### 2. `core/runner.py`

- 新增 `_first_seen_map()`：读 `断货分析/型号首库存登记.xlsx` → `{SKU: 首现日期}`
- `apply_shipments()` 里新增**新品补行**，位置在 `ships = Sh.load_shipments(...)` **之前**、
  且**不依赖 `mine` 是否为空** —— 这是关键：原来 `if not mine: return` 会让零货件的表直接返回，
  补行永远走不到（G599~G601 就是这么漏掉的）。

判据链：
```
库存源里有该 SKU
  → listing 活着（afn-listing-exists=Yes，或来自自建「可售库存」）
  → 分析表 A 列没有
  → 首现日期 >= 当月 1 号
  ⇒ 补行，D 列按 listing 写「在售/未上架」
```

### 3. `pipeline/run.py`

跑批前先刷新登记表（`tools/first_stock_register.py --apply`），失败只提示不阻断。

### 4. `pipeline/tools/maintenance/patch_pink_exclude_unlisted_20261023.py`（新建）

XML 层给 16 张分析表的 4 条粉色规则各加一条 D 列排除：

```
AND($A7<>"",N($F7)<=0,...)  →  AND($A7<>"",$D7<>"未上架",N($F7)<=0,...)
```

走 XML 不走 openpyxl 的原因同 §G：openpyxl 存盘会清空公式缓存值。
幂等（已含「未上架」跳过）；12 本全部落盘，64 条规则。

### 5. `pipeline/tools/first_stock_register.py`（新建）

扫 **3 期 × 12 个快照日 × 207 份库存报告**，产出
`断货分析/型号首库存登记.xlsx`：

- sheet「首库存登记」：468 行，一行一个 SKU
  `SKU / 型号 / 首次出现 / 首可售日 / 首在途日 / 首可售站点 / 首在途站点 / 当前可售 / 当前在途 / 涉及站点数 / 状态`
- sheet「站点明细」：5368 条，一行一个 (SKU, 站点)，看具体哪天在哪个站点有货

**「真正有库存」的口径**：`首可售日` = 第一次 `afn-fulfillable-quantity > 0`。
在途单独一列（`首在途日`）—— 在途不等于有库存，只有可售 > 0 才算能卖。

## 五、已知问题

**① 沙箱删除配额会让跑批在收尾阶段失败**

现象：`run.py` 退出码 1，但**没有任何跑批日志**，报
`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":78,"threshold":50,"scope":"turn"}`。

根因：保真管线每本簿要删 2~4 个中间文件（`.new.xlsx` / `.rec.tmp` / `.rs.tmp` /
`.pivotstrip.xlsx`），12 本 + 体检/归档累计下来会超过 **每个 turn 50 次删除**的配额，
删除被拒 → Python 抛异常 → 进程退出。`--jobs 1` 也救不了，因为配额是 per-turn 累计的。

**数据不会坏**：失败发生在收尾阶段，正式文件保持上一次成功跑批的结果；中间文件残留在
`1.每日销售数据表/` 下，用 `python -c "import os,glob; [os.remove(f) for p in [...] for f in glob.glob(p)]"`
清掉即可。**恢复办法：新开一个会话再跑**（配额按 turn 重置）。

2026-10-23 实测：一次全量跑 + 两次单簿跑 + 一次清理中间文件，累计删除 78 次触发配额；
三处补行（欧盟 70 行 / 日本 SKU139 / Interflowd北美 G455）分别在三次**成功**的跑批里已落盘。

**最终结论（当日 18:39 全量跑批 EXIT=0，12/12 本归档）**：批次自身的删除量 ~36 次不超线，
超配额全是「同 turn 内先手动清理了中间文件」把计数累过 50。**要跑批就开新 turn 直接跑，
别在同 turn 里做任何手动文件清理**；残留中间文件留到跑完后的新 turn 再清。

**② 跑批后公式缓存值是空的**（`<v />`）。
欧盟表 26037 个公式全部无缓存值，`openpyxl(data_only=True)`、预览面板、归档比对读到的都是 None。
Excel 打开会自动重算，人工看表正常。

这是 openpyxl 保存的固有行为，不是本次引入。要彻底解决，得在跑批后补一遍重算
（Excel COM / LibreOffice headless），或者把「只改 XML」的保真写法推广到整个跑批。
