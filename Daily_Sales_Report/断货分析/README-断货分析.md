### 需求A · 缺货三级标记（用户口径，勿改）

| 级别 | 判定 |
|---|---|
| 一级 | 库存不为 0，且 **可售天数 + 7 < 计划备货天数** |
| 二级 | 库存 0，**在途 > 0** |
| 三级 | 库存 0，**在途 0** |

计划备货天数取 `断货分析/备货天数.xlsx`（唯一副本，15 个站点）。

#### 三级内部再分一层「未起量」（2026-10-29 新增）

三级里有一部分 SKU **今年一件都没卖过**，它们不是「最紧急的断货」而是「还没起量」，
单独成表、不计入缺货数（`--keep-unsold` 可回到旧口径）。

| 情况 | 处理 |
|---|---|
| 三级 · 无在途 · 今年卖过 | 留在三级，是真断货 |
| 三级 · 无在途 · 今年从没卖过 | 进「未起量」sheet，不计入缺货数 |
| 二级（有在途） | **一律不拆** —— 货已在路上，是标准缺货 |

**为什么不能按「近30天没销量」筛**：可售为 0 的 SKU 本来就没货可卖，
近30天销量 0 是**结果**，不能证明没需求。实测 20261028：

- 326 个近30天无销量的缺货 SKU，**listing 一个都没下架**（全部 `afn-listing-exists=Yes`）
- 其中 103 个今年卖过（47 个 9 月还在卖）→ 真断货
- 只有 223 个是今年从没卖过的
- 站点反差极大：印度主账号 86 个无销量里 76 个从没卖过；美客多墨西哥 78 个里 64 个卖过

**判据来源**：各簿「-每日库存分析表」的月度块（跑批封存的 1~12 月销量）。
全 0 行在解析阶段就被跳过，所以「查不到」= 今年没卖过。读不到月度块时**退化为不拆**。

实测 20261028 改造后：缺货 1788 → **1600**（一级 1274 / 二级 222 / 三级 104），
未起量 188 个单列。

> ⚠️ 断货明细（`stockout_report.py`）仍按原口径全量列出（1788），
> 它的 P3「无动销断货」= 缺货表里的「未起量」。两者数字不同是**有意的**：
> 缺货表是汇总（只列要补的），断货明细是明细（全量可查）。

## 三、三个产出分别是什么

| 产出 | 脚本 | 触发 | 回答什么问题 |
|---|---|---|---|
| **每日缺货情况表** | `pipeline/tools/shortage_report.py` | 随 `pipeline/run.py` 自动 | 哪些 SKU 快断了？分三级：一级「可售天数+7 < 计划备货天数」/ 二级「库存0有在途」/ 三级「库存0无在途」（三级再拆「未起量」） |
| **断货明细 + 断货报告** | `pipeline/tools/stockout_report.py` | 随 `pipeline/run.py` 自动（2026-10-28 起） | 断货原因是什么？按地区汇总、给采购建议、带呆滞判断 |
| **东南亚缺货 60 天明细** | `pipeline/tools/sea_stockout_detail.py` | 手动 | 东南亚哪些在售品已经断货？断货前 60 天卖得怎么样（按国家、月份分 sheet） |

> 每日缺货表**复用** `stockout_report.build()` 的读取逻辑，两套不会算出不同数字。
> 实测 20261023：二级 289 / 三级 292，与断货明细的「一般 289 / 严重 292」完全一致。
> 实测 20261028：二级 222 / 三级 292，断货明细「一般 222 / 严重 292」，再次一致。
>
> ⚠️ 2026-10-29 起缺货表把三级里「今年从未有过销量」的拆到「未起量」sheet，
> 所以**三级的数字会比断货明细的「严重」少**（20261028：104 vs 292，差 188）。
> 一级/二级不受影响，仍与断货明细的「预备/一般」一致。

### 每日缺货表里的「采购建议」sheet（2026-11-03 新增）

给采购直接下单用，只列**建议数量 > 0** 的 SKU，按**数量梯队**排序（T1 大单 → T4 碎单），末行带合计数。

| 项 | 口径 |
|---|---|
| 目标覆盖天数 | **计划备货天数**（同一份 `备货天数.xlsx`，与表内「计划备货天数」同源） |
| 目标库存量 | `ceil(计算日均 × 计划备货天数)` |
| 建议数量 | `目标库存量 − 可售库存 − 在途`（预留已锁定给既有订单，**不减**） |
| 含在途可撑天数 | `(可售 + 在途) ÷ 计算日均`。它 **<** 计划备货天数 ⇔ 建议数量 **> 0**，可逐行自校验 |

**采购动作**（2026-11-03 按用户要求从一整串文字拆成独立列，供 Excel 直接筛选）：

| 采购动作 | 对应等级 | 含义 | 本批行数 |
|---|---|---|---:|
| 立即补货 | 三级 | 可售与在途都是 0，已无货可卖 | 115 |
| 在途不足 | 二级 | 有在途但撑不到计划天数，建议下周三前到 | 65 |
| 排入下周三 | 一级 | 还能撑几天，按节奏排单 | 189 |

> 拆列前「采购建议」是一列长文字（`补货 156 件（在途不足）`），筛选只能做文本包含匹配；
> 拆开后「采购动作」是纯枚举值、「建议数量」是纯数字，筛选 / 求和 / 透视都能直接用。
> 原来的「建议时机」列已删除 —— 它与「采购动作」一一对应，留着只会占位并让筛选多一层歧义。

**计算日均的回退链**（断货 SKU 本月常常没货可卖，不回退会把建议量算成 0）：

```
本月日均（实时速度，已剔除当月缺货天数）
  → 为 0 时退 上月日均
  → 再为 0 时退 近3月销量 ÷ 90
  → 再为 0 时退 近30天 ÷ 30
```

实际用了哪一档写在「日均来源」列，采购可据此判断这个建议量有多可信。

**优先级**（与断货明细同一套逻辑：严重断货=三级、一般断货=二级、预备断货=一级）：

| 优先级 | 条件 |
|---|---|
| P0 | 三级 且 近30天 ≥ 5 件 |
| P1 | 二级/三级 且 近30天 ≥ 1 件 |
| P2 | 一级（可售不足） |
| P3 | 二级/三级 且 近30天 = 0 |

`--moq N` 按 N 件/箱向上取整（默认 0 = 不取整），是否取整会写在 sheet 第 1 行说明里。

**数量梯队**（2026-11-03 加，整表主排序按它从大到小）：

| 梯队 | 建议数量 | SKU 数 | 合计件数 | 占件数 |
|---|---|---:|---:|---:|
| T1 大单 | ≥ 200 件 | 0 | 0 | 0% |
| T2 中单 | 51 ~ 199 件 | 5 | 512 | 15.1% |
| T3 小单 | 11 ~ 50 件 | 78 | 1770 | 52.2% |
| T4 碎单 | ≤ 10 件 | 240 | 1108 | 32.7% |

> ⚠️ 上表是 **2026-11-03 深夜别名归并之后**的分布。当天早些时候的版本 T1 曾有
> 31 行 / 16148 件（76.5%）——后来证实**整档都是 `amzn.gr.*` 别名幻影**（见下节），
> 归并后 T1 清零、采购合计从 21105 → 3390 件。
>
> 边界不是等分，是照真实分布切的。改档位只需改 `_TIER_BOUNDS`，排序、序号、表尾汇总会一起跟着变。
>
> 「梯队内序号」= 该档里按数量从大到小的第几单，采购可以「T2 第 1 单、第 2 单…」逐批下单。
> 按梯队排之后，**P0 不一定在表头上**：想看急迫度就筛「采购动作 = 立即补货」，别看行号。

**amzn.gr.\* 别名行归并**（2026-11-03 深夜，修「库存 0 却喊补 2392 件」）：

- 现象：欧盟/英国库存报告里，同一 ASIN 会拆成「裸 SKU + `amzn.gr.<SKU>-<hash>[-LN|-VG|-PO]`」
  两行（欧盟 45 行 / 英国 238 行）。别名行经常 0 库存，单独成行被判三级断货、
  按月度块历史日均算出天价补货单 —— G520 实测建议 2392 件，而同 ASIN 的裸 G520 行
  有 677 可售 + 19 预留 + 1242 在途。一件东西两张嘴。
- 修法：库存行、订单销量 key、库龄挂接三处统一按 `analysis.normalize_sku` 归并
  （与月度块 A 列同规则，2026-10-27 起）；数量求和，行名用基础 SKU，
  判定依据里注记「（并 N 个 amzn.gr.* 别名行：…，库存已求和）」。
- 顺带把 `_SKU_HEAD_RE` 从 `\d{3,4}` 放宽到 `\d{2,4}`：两位数基础 SKU（G53/G86/G94/G95/G98）
  的别名原来归并不掉。这也修掉了月度封存侧同类丢销量的问题（与 2026-09 英国少 8 件同源）。
- 效果：缺货 693 → 647（三级 168 → 122，消失的全是别名行）；一级/二级不变；
  采购建议 369 → 323 行、21105 → 3390 件；未起量 143 → 141。
  控制台以「[别名归并]」单独提示，不与「数据异常」混排。

#### 2026-11-03 修复：主明细表「缺口天数」口径不一致

`gap` 原先用 `r["dos"]`（近30天日均口径）算，而「可售天数」列显示的是 `dos_v`
（本月日均口径，2026-10-29 换过来的），于是出现 **可售 6 天 + 后勤 7 天 + 缺口 48 天 ≠ 计划 75 天**。

现已改用判级所用的 `dos_use`，与显示列同源。五个 sheet 全量校验：

| sheet | 恒等成立 | 留空 |
|---|---:|---:|
| 一级 | 317 | 0 |
| 二级 | 43 | 165 |
| 三级 | 30 | 138 |
| 未起量 | 0 | 143 |

恒等式 = `可售天数 + 后勤周期7 + 缺口天数 == 计划备货天数`，不成立 0 例。

> **留空是刻意的**：本月一件没卖的 SKU，本月日均=0，可售天数按日销表口径显示 "-"，
> 缺口天数便无从谈起（不编一个假装精确的数）。这类行看「判定依据」列的
> 「库存 0，在途 N 件」即可；要补多少看「采购建议」sheet 的「计算日均」（会回退到上月/近3月）。
>
> 同时修正了断货明细「采购建议」sheet 的过时文案：原文写死 `ceil(日均×14)`，
> 实际是按各站点计划备货天数算（美客多 156=2.6×60）。
>
> 实测 20261103：缺货 693 个 → 有采购建议 369 个（P0 8 / P1 39 / P2 189 / P3 133），
> 合计建议补货 21105 件；另 324 个因在途已覆盖目标库存而不列入。

## 四、怎么跑

### 亚马逊（随日销表，两个产出都自动）

```bat
cd /d C:\Users\dell\Desktop\work-main\sale_file_gen\Daily_Sales_Report
python pipeline\run.py --snap ..\trunk\data\数据归属周期\202610\快照日期\20261028
```
run.py 在 runner 成功后**依次**自动生成：
1. 每日缺货情况表（`--no-shortage` 可关）
2. 断货明细 + 断货报告（`--no-stockout` 可关，2026-10-28 新增）

两者都是「失败只提示、不阻断」：断货明细异常只会打一行 `[断货明细] !! ...`，
跑批退出码、归档结果都不受影响。--dry-run 两者都不出。

单独重出（口径与自动跑完全相同，都是同一支脚本）：
```bat
python pipeline\tools\shortage_report.py --snap <快照目录>
python pipeline\tools\shortage_report.py --lead 7      # 后勤周期，默认 7 天
python pipeline\tools\shortage_report.py --moq 12      # 采购建议按 12 件/箱向上取整（默认不取整）
python pipeline\tools\stockout_report.py --snap <快照目录>
```

### 东南亚（单独跑，不跟日销表）

```bat
python pipeline\tools\sea_stockout_detail.py              # 默认口径
```
